# 業務プロセスと責任分界

## 1. 工程分解

案件調査 → 企画（訴求軸・台本設計）→ コンプライアンス事前チェック → 制作（撮影・編集）
→ 入稿 → 計測 → 分析 → 改善 → 報告

## 2. AI/人間の責任分界

| # | 工程 | 内容 | 担当 | 対応する仕組み |
|---|---|---|---|---|
| 1 | 案件調査 | 新規カテゴリ比較、ASP規約リスク洗い出し | **AIが下調べ／人間が確定判断** | `offer-researcher`（→ docs/01_offers.md） |
| 1' | ASPへの確認事項の送信 | SNS広告可否・LP改変可否等をASPに問い合わせる | **人間のみ（自動化しない）** | docs/01_offers.md の質問テンプレートを人間がコピペ送信 |
| 2 | 企画 | 訴求軸・フック・絵コンテのドラフト作成 | **AI中心／人間が選定・修正** | `creative-writer`、`/new-creative`（→ docs/03_creative.md） |
| 3 | コンプライアンス事前チェック | 薬機法・景表法・媒体ポリシーとの照合 | **AIが一次チェック／人間が最終承認** | `compliance-checker`、`/check`（→ docs/02_compliance.md） |
| 4 | 制作（撮影・編集） | 動画の実撮影・編集 | **人間のみ**（物理作業、外注なし） | 対象外（AI化しない） |
| 5 | 入稿 | 広告アカウントへのアップロード・配信設定・金額設定 | **人間のみ（自動化しない）** | 実際の広告費が動き、アカウント停止リスクがあるため |
| 6 | 計測 | 媒体管理画面から実績CSVをエクスポート | **人間のみ** | `data/raw/` に手動配置（→ data/schema.md） |
| 7 | 分析 | 撤退基準の判定（continue/increase/decrease/stop） | **AIが一次判定／人間が最終アクション決定** | `scripts/analyze.py`、`performance-analyst`、`/analyze`（→ docs/04_budget.md） |
| 8 | 改善 | クリエイティブ差し替え・予算増減の判断 | **AIが提案／人間が実行** | `performance-analyst` の提案を人間が広告アカウント上で実行 |
| 9 | 報告 | 出資者向け週次/月次レポート | **AIが草案作成／人間が確認・送付** | `report-writer`、`/weekly`（→ docs/07_reporting.md） |

### 自動化しない領域（明示的に人間専任）
- 法務チェックの最終承認（薬機法・景表法・媒体ポリシー適合の最終判断）
- 広告アカウントへの実際の入稿・配信設定
- 予算増減の実行（広告アカウント上での金額変更操作そのもの）
- 出資者への報告の送付（内容はAIが草案作成するが、送付は人間が行う）
- ASPへの問い合わせ送信（案件確認事項の実送信）

これらは「AIが提案・下書き・一次チェックまでは行うが、実行・最終承認は必ず
人間が行う」という一貫したルールに基づく。理由は、①広告費・アカウント停止という
金銭的・事業継続リスクが直接発生する操作であること、②法務・出資者対応は
対外的な責任が伴う意思決定であること、の2点。

## 3. MVPで最初に作るべきもの（優先順位）

自分1人運用・月予算100万円という制約の中で、最小構成から立ち上げる場合の
優先順位は以下の通り。

1. **`/check` + `compliance-checker`** — 撮影・入稿前の安全網を最初に用意する。
   アカウント停止・法令違反は事業継続そのものを止めるリスクであり、他の何より先に
   機能させるべきガードレール。
2. **`/new-creative` + `creative-writer`** — 検証を回すには撮影素材（台本）の
   供給が必要。docs/03_creative.mdの15フックはすでにあるため、次のバッチを
   量産する仕組みとして早期に整備する。
3. **`scripts/analyze.py` + `/analyze` + `performance-analyst`** — 実際に広告が
   配信され実績データが出始めた段階で必要になる。検証フェーズ開始と同時に使える
   状態にしておく。
4. **`/weekly` + `report-writer`** — 出資者資金で運用している以上、報告サイクルは
   早期に確立すべきだが、実績データが貯まる前は空疎な報告になるため、
   優先順位としては分析基盤の後でよい。
5. **`offer-researcher`** — 本命案件（リビンマッチ）が既に確定しているため、
   当面は不要。案件を分散・拡張するタイミング（サブ案件の実績が出た後）で
   優先度が上がる。
